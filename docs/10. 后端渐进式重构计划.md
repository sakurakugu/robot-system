# 10. 后端渐进式重构计划

## 结论

当前云端后端需要重构，但不建议整体重写。

- `app/robot-cloud/后端` 已经有模块化雏形，业务功能也能继续开发。
- 但数据库访问、WebSocket 服务、编舞系统服务这几块已经进入“需要结构性收口”的阶段。
- 适合采用“分阶段替换 + 保持接口稳定”的渐进式重构，不适合停下来推翻重做。

## 范围

- `app/robot-cloud/后端`

本轮先不覆盖：

- `app/robot-agent/robot-server`
- `app/robot-agent/robot-agent`
- `app/robot-cloud/前端`
- `app/robot-phone/RobotPhone`

## 当前判断依据

### 1. 数据库访问层已经是结构性瓶颈

1. 当前数据库访问不是标准异步 `pg` 调用，而是“worker 线程 + 同步等待”的包装。
- `src/core/database/sync-pg.ts` 中通过 `SharedArrayBuffer + Atomics.wait` 阻塞当前线程等待结果。
- 这种实现方式会把 Node.js 本该擅长的异步 I/O 重新拉回同步等待模型。

2. 数据库 worker 连接池被限制为 `max: 1`。
- 这意味着数据库操作天然串行化。
- 当请求量增加、鉴权频繁、WebSocket 事件变多时，吞吐会明显受限。

3. 当前认证链路会放大数据库压力。
- `withAuthContext` 是全局中间件。
- 带 token 的请求会额外触发 session 和 user 查询，以及 `last_seen_at` 更新。
- 在当前同步数据库模型下，这些“每请求必经”的操作会把阻塞扩散到整个 API 链路。

### 2. 应用装配方式耦合偏重

1. `src/app.ts` 同时负责：
- 创建 Express 应用
- 创建数据库服务
- 创建 WebSocket 服务
- 创建所有业务 service
- 创建所有 controller
- 配置中间件
- 配置路由
- 处理服务之间的延迟注入

2. 当前大量依赖通过 `setXxxService()` 方式在构造后补注入。
- 说明依赖方向不够清晰。
- 这会让测试、替换实现、按模块拆分都变困难。

### 3. WebSocket 服务已经成为巨石类

1. `src/modules/websocket/service.ts` 文件过大。
- 当前文件规模已经达到 2000+ 行。
- 文件同时承担连接管理、UI 鉴权、消息路由、音频上传下载、ASR、TTS、LLM 对话、机器人控制桥接、请求响应等待等职责。

2. 同类逻辑重复较多。
- 拍照、音量、配置、SDK 模式、日志标记、安装包推送等能力都采用近似重复的“发送消息 + 监听响应 + 超时”写法。
- 后续继续增加机器人能力时，重复代码会继续增长。

3. 当前实现有潜在监听器泄漏风险。
- 多处 `new Promise + websocket.on('message') + timeout` 逻辑在超时时仅 `reject`，没有统一清理监听器。
- 服务长时间运行后，调试和稳定性风险会越来越高。

### 4. 编舞系统服务职责过多

1. `src/modules/编舞系统/service.ts` 同时承担：
- 项目管理
- 文件管理
- 导入导出
- 自定义动作管理
- 音频资源管理
- 时间轴编译
- 执行调度
- 机器人连接测试
- SSH/Python 执行桥接

2. 大量同步文件 I/O 直接运行在请求线程中。
- 当前有较多 `fs.readFileSync`、`fs.writeFileSync`、`fs.rmSync`、`fs.renameSync`。
- 文件操作重一点时，会直接阻塞 Node 事件循环。

3. 路径安全校验仍然比较粗糙。
- 现在主要依赖 `path.join(...)` 后再做前缀判断。
- 在 Windows 环境下，这类判断方式不够稳妥，后续应统一改成 `path.resolve` 后基于根目录边界校验。

### 5. 测试基线明显不足

1. 当前后端已经有 `jest` 依赖，但仓库内缺少稳定的测试基线。
2. 在没有最小回归测试保护的情况下，大规模重构的风险会明显上升。
3. 后端已不再是“只有几个接口的小项目”，应至少补齐：
- 健康检查
- 登录与鉴权
- 核心机器人接口
- 关键 WebSocket 请求响应桥接

## 不做的事

- 不把后端整体改写为 NestJS。
- 不在第一轮就把 `ws` 更换为 Socket.IO。
- 不在第一轮就引入重 ORM。
- 不为了“架构更现代”而大规模重命名、迁移全部目录。
- 不在没有测试基线前，同时改协议、改数据库层、改前端联动。
- 不一次性追求所有 `any` 清零。

## 重构原则

1. 先解决阻塞和耦合，再做风格统一。
2. 先抽基础设施边界，再拆巨石业务文件。
3. 第一轮尽量保持 REST 路由和 WebSocket 消息协议不变。
4. 每次只处理一个大问题，避免多个高风险改动叠加。
5. 每完成一个阶段，都要跑 `lint`、`typecheck`，并补对应测试。

## 优先级

### P0：先建立重构保护带

目标：
- 让后续重构有最小回归保护。
- 先修补最明显的稳定性问题。

先做这些：
- 补最小测试基线。
- 抽 WebSocket 通用请求响应桥接器，消除重复逻辑。
- 修复超时后监听器未清理的问题。

### P1：重构数据库访问层

原因：
- 这是当前最核心的基础设施问题。
- 不先处理数据库层，后面所有模块拆分都会建立在错误的 I/O 模型上。

目标：
- 去掉 `sync-pg.ts` 的同步等待实现。
- 改为标准异步 `pg` 客户端。
- 按业务模块拆 repository，而不是继续维护单体数据库服务。

### P2：重构应用装配与依赖注入

原因：
- 当前 `app.ts` 负责太多初始化与服务编排。
- 只有把依赖方向理清，后面拆 WebSocket 和编舞系统才不会继续互相缠绕。

目标：
- 抽出 `bootstrap` 层。
- 用显式构造参数代替大部分 `setXxxService()`。
- 让每个模块都能在测试中独立实例化。

### P3：拆分 WebSocket 巨石服务

原因：
- 它已经是当前后端最复杂、最难改的一块。
- 很多“功能还能加，但越来越不敢动”的现象都集中在这里。

拆分目标：
- 连接注册
- UI 连接鉴权
- 消息分发
- 机器人命令请求响应桥接
- 音频会话管理
- 对话输入编排

### P4：拆分编舞系统服务

原因：
- 文件服务和执行调度混在一起，后续维护风险高。
- 同步文件 I/O 会持续拖慢请求处理。

拆分目标：
- 项目存储层
- 路径安全与文件操作层
- 编舞业务服务
- 执行调度服务
- 机器人连接与外部执行桥接

### P5：最后做类型与错误模型收口

目标：
- 统一错误处理。
- 减少 `any`。
- 清理 lint warning。
- 让后续继续迭代时不再反复回头补基础规范。

## 建议的阶段落地顺序

### 阶段 0：建立基线

目标：
- 明确重构前的最小保护范围。

内容：
1. 补后端测试基础设施。
2. 增加以下最小测试：
- `GET /api/v1/health`
- 注册 / 登录 / 鉴权
- 一个核心业务接口
- 一条 WebSocket 请求响应链路
3. 抽离 WebSocket 通用 `request-response` 跟踪器。

验收：
- 新增测试能稳定运行。
- WebSocket 请求响应桥接不再到处复制粘贴。

### 阶段 1：数据库层异步化

目标：
- 去掉当前“伪同步数据库”模型。

内容：
1. 新增 `src/core/db/`。
2. 封装标准异步 `pg` 客户端与事务工具。
3. 按模块逐步新增 repository：
- `account-repository.ts`
- `robot-repository.ts`
- `settings-repository.ts`
- `knowledge-repository.ts`
4. 保持接口行为不变，先从最小模块替换。

验收：
- 运行时不再依赖 `Atomics.wait`。
- 核心接口行为不变。
- `lint` 和 `typecheck` 通过。

### 阶段 2：重构应用装配层

目标：
- 把创建对象和业务逻辑解耦。

内容：
1. 新增 `src/bootstrap/create-context.ts`。
2. 新增 `src/bootstrap/create-app.ts`。
3. 把 `app.ts` 收缩为“应用组装器”。
4. 把 `server.ts` 收缩为“启动入口”。

验收：
- `app.ts` 不再手工编排全部服务细节。
- 主要依赖能在构造期明确注入。

### 阶段 3：拆 WebSocket 服务

目标：
- 让 WebSocket 逻辑可维护、可测试、可继续扩展。

内容：
1. 新增：
- `connection-registry.ts`
- `ui-auth.ts`
- `message-router.ts`
- `robot-command-gateway.ts`
- `audio-session-manager.ts`
- `conversation-gateway.ts`
2. REST 侧统一调用 `robot-command-gateway`。
3. 所有请求响应桥接统一走同一套超时和监听清理逻辑。

验收：
- `websocket/service.ts` 显著缩小。
- 新增机器人指令时，不再复制整段等待响应代码。

### 阶段 4：拆编舞系统服务

目标：
- 让编舞系统从“超级 service”变成多个可替换子模块。

内容：
1. 新增：
- `storage/project-storage.ts`
- `storage/path-resolver.ts`
- `choreo-service.ts`
- `choreo-execution-service.ts`
2. 文件操作统一迁移到 `fs/promises`。
3. 统一路径解析和安全校验。
4. 调度和文件管理彻底分离。

验收：
- 文件访问不再散落在业务流程中。
- Windows 路径边界校验通过。

### 阶段 5：收口与清理

目标：
- 把第一轮重构形成稳定基线。

内容：
1. 统一错误对象和错误响应。
2. 清理明显 `any` 与弱类型边界。
3. 清理 lint warning。
4. 补核心回归测试。

验收：
- 工程警告数量下降。
- 关键模块具备稳定测试覆盖。

## 每阶段验收标准

- 当前阶段核心接口行为不回退。
- `npm run lint` 通过。
- `npm run typecheck` 通过。
- 新抽出的模块边界清晰，不产生新的超级工具文件。
- 改动后能继续为下一阶段复用，而不是一次性补丁。

## 当前实施建议

如果按“风险最低、收益最高”的顺序推进，建议这样做：

1. 先做阶段 0。
2. 再做阶段 1 的基础设施与账号模块迁移。
3. 然后做阶段 2，理顺依赖方向。
4. 最后再进入 WebSocket 与编舞系统的正式拆分。

原因：
- 没有测试基线时，不适合直接大拆数据库层和 WebSocket。
- 数据库层不先改，后面所有拆分都会继续受阻塞模型影响。
- 装配层不先理顺，WebSocket 和编舞系统拆分会不断引入新的互相注入。

## 说明

这份文档的目标不是一次性定死最终架构，而是先把“为什么要重构、先动什么、哪些事暂时别动、每一步如何验收”写清楚。

后续可以按阶段持续更新文档中的“第一批任务”和“当前实施建议”，让它作为后端重构的持续记录，而不是一次性的讨论结论。
