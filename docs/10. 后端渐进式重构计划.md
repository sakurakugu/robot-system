# 10. 后端渐进式重构计划

## 结论

截至 `2026-03-30`，云端后端重构已经完成了前半段，当前不需要推翻重写，但仍然有几块明确的尾项和下一阶段重点。

- `app/robot-cloud/后端` 的异步 `pg` 基础设施、模块化 repository、`bootstrap` 装配层、编舞系统首轮拆分、WebSocket 请求响应跟踪器已经落地。
- 旧文档里“先补测试、先做异步数据库基础设施、先拆编舞系统大块职责”这几件事，已经基本完成。
- 现在最优先的工作已经不是继续大拆编舞系统，而是：
  1. 继续拆 `WebSocketService` 巨石。
  2. 收口错误模型、类型边界和剩余同步文件 I/O。
  3. 继续压缩依赖注入和模块边界。

## 当前仍然需要重构的部分

### P0：继续拆 `WebSocketService`

这仍然是当前最大的复杂度来源。

当前问题：

- `src/modules/websocket/service.ts` 仍然有 2000+ 行。
- 同时承担连接管理、UI 鉴权、消息分发、音频会话、ASR、TTS、对话编排、机器人命令请求响应桥接等职责。
- 当前仍然依赖多处 `setXxxService()` 延迟注入。
- `any` 和弱类型主要集中在这个文件。

建议拆分方向：

- `connection-registry.ts`
- `ui-auth.ts`
- `message-router.ts`
- `robot-command-gateway.ts`
- `audio-session-manager.ts`
- `conversation-gateway.ts`

### P2：继续收口依赖注入和循环依赖

虽然 `bootstrap` 已经存在，但依赖方向还没有完全理顺。

当前问题：

- `create-app-context.ts` 里仍然有一串对象创建后再 `setXxxService()` 的装配。
- `机器人服务`、`编舞服务`、`编舞执行服务`、`WebSocketService` 之间仍有延迟注入痕迹。

目标：

- 能构造时注入的依赖尽量在构造时注入。
- 必须晚绑定的能力改成更明确的小接口，而不是直接相互持有整个大服务。
- 主要模块应能在测试中独立实例化，不依赖隐含初始化顺序。

### P1：继续清理剩余同步文件 I/O

上一轮已经清掉更新管理、机器人包管理、Python 执行器和编舞导入链路里的同步文件 I/O，但当前还残留几处基础设施级同步调用：

- `src/server.ts` 中启动期 migration 仍然使用 `execFileSync`。
- `src/core/logger/index.ts` 中日志目录初始化仍然使用 `existsSync` / `mkdirSync`。

目标：

- 将剩余同步文件 / 启动阻塞点压缩到最小范围。
- 只在确有必要时保留启动期同步行为。

### P1：收口错误模型与类型边界

这已经进入可以系统治理的阶段。

当前问题：

- 控制器里仍有大量重复的 `try/catch + res.status(...)` 模板代码。
- 错误码和错误类型没有统一模型。
- 非测试代码里仍然存在较多 `any`。
- WebSocket、控制器、日志工具仍然有较多弱类型边界。

目标：

- 统一领域错误 / HTTP 错误映射。
- 清理主要路径上的 `any`。
- 将高频的参数解析和响应模板抽成基础设施。

### P1：继续收口编舞项目机器人配置边界

这条仍然保留旧文档的建议，并且现在依然成立。

当前问题：

- 编舞系统里的项目机器人配置和项目机器人关联目前仍然都落在 `robots.json`。
- `ChoreoRobot` 和 `ProjectRobotConfig` 共享同一文件存储边界，语义上仍然偏混合。

目标：

- 为项目机器人配置补更清晰的 storage / repository 接口。
- 明确“关联主机器人表的项目机器人”和“项目内直连机器人配置”的数据边界。

### P2：后续再拆 `机器人服务`

`src/modules/机器人管理/service.ts` 当前仍然职责偏多：

- 仓库读写
- SSH 初始化
- 连通性检测
- WebSocket 命令代理
- 安装包推送
- 音频路由配置读写

这不是当前最急，但会是 `WebSocketService` 之后的下一块重点。

## 不做的事

- 不整体改写为 NestJS。
- 不把 WebSocket 第一轮直接改成 Socket.IO。
- 不为了“更现代”而整体挪目录或全量重命名。
- 不在没有明确收益的情况下追求一次性清空所有 `any`。
- 不在同一轮同时修改协议、数据库层、WebSocket 路由和前端联动。

## 重构原则

1. 先删遗留基础设施，再拆当前最大复杂度热点。
2. 先收口依赖方向，再做风格统一。
3. 每次只推进一个高风险问题，避免重构项叠加。
4. 第一轮继续尽量保持 REST 路由和 WebSocket 消息协议稳定。
5. 每完成一个阶段，都要跑 `npm run lint`、`npm run typecheck`、`npm test`。

## 建议的后续阶段顺序

### 阶段 A：移除旧同步数据库层（已完成）

目标：

- 彻底结束双数据库访问模型并存状态。

内容：

1. 为系统路由补异步统计依赖。
2. 将启动期机器人离线重置迁移到异步 `robot repository`。
3. 将默认角色初始化迁移到异步 `role repository` 或独立 bootstrap 初始化函数。
4. 删除 `src/core/database/` 旧实现及其引用。

验收：

- 运行时代码不再依赖 `Atomics.wait`。
- 应用启动不再实例化 `DatabaseService`。
- 系统状态接口行为不变。

### 阶段 B：拆 `WebSocketService`

目标：

- 将 WebSocket 从巨石类拆成多个可组合部件。

内容：

1. 抽连接注册与路由分发。
2. 抽 UI 鉴权。
3. 抽机器人命令网关。
4. 抽音频会话管理。
5. 抽对话输入编排。
6. 将大部分 setter 注入收口为构造依赖或更小接口。

验收：

- `websocket/service.ts` 显著缩小。
- 新增机器人指令时不再复制样板代码。

### 阶段 C：文件 I/O、错误模型、类型边界收口

目标：

- 让剩余基础设施风格统一。

内容：

1. 清掉 `server.ts`、`logger` 等剩余同步文件 I/O / 启动阻塞点。
2. 抽统一错误类型和错误响应映射。
3. 收口控制器重复样板。
4. 按高频路径清理 `any`。

验收：

- 高频请求链路不再包含明显同步阻塞点。
- 控制器代码长度和重复度下降。
- 关键模块的类型边界更清晰。

### 阶段 D：继续压缩机器人与编舞剩余边界

目标：

- 让模块边界从“能拆”进入“清晰可维护”状态。

内容：

1. 明确编舞项目机器人配置的独立存储接口。
2. 拆 `机器人服务` 中 SSH / WebSocket / 仓库职责。
3. 根据实际复杂度决定是否需要新的 facade / application service 层。

验收：

- 模块依赖方向更单一。
- 新功能增加时不再优先改大文件。
